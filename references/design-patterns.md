## Designer 决策规则

设计模式是对反复出现的设计压力的一种候选解法，不是架构质量徽章。本手册是按需查阅的离线目录，不是设计前的
必读清单：只有当某个 Task 存在非平凡结构决策时才查阅，并借助[快速索引](#快速索引)直接跳到相关模式。对这类
Task 回答以下问题：

1. 当前代码中是否存在一个具体、已经发生或由已确认需求必然产生的设计压力？哪个模式可能缓解它，收益是什么？
2. 如果收益真实且大于代价，模式应在什么最小边界内应用，由哪些参与者承担哪些职责，怎样验收收益？

采用模式必须同时通过这些门槛：

- **有证据的压力**：能指出变化轴、重复、耦合、生命周期、组合、状态或算法替换问题；“以后也许会扩展”不算。
- **简单方案不足**：先写出直接函数、普通数据结构、模块边界、依赖注入或小范围条件分支等更简单方案，并说明其
  为何无法满足当前约束。
- **净收益为正**：收益必须落到正确性、可测试性、可替换性、复用、性能、内存、故障隔离或认知负担中的至少一项，
  并明显大于新增抽象、对象数量、间接调用、状态同步和调试成本。
- **边界足够小**：只在压力真实存在的边界内应用，不为一个模式额外拆 Plan、Task、服务、包或无行为的接口层。
- **参与者正确**：模式的各角色、所有权、数据流、错误语义和生命周期明确，不能只使用模式名称包装普通代码。
- **收益可验收**：测试或静态检查能证明关键替换、组合、状态迁移、资源共享或访问控制确实成立。

`none` 是正常且常常更好的结论。若直接实现已经清晰稳定，Designer 应明确拒绝模式，而不是制造扩展点。语言原生的
函数、模块、协议、迭代器、事件、数据类和依赖注入已经解决问题时，也不应再机械复刻面向对象结构。

当且仅当 Designer 真的评估过某个候选模式时，把如下记录写进该 Task 的 `design` 字段（例如
`design.patterns`）。没有评估过模式的 Task 不需要这条记录，也不要为了填表而虚构候选：

```text
pattern_catalog: refactoring-guru-catalog-22-v1
candidate: <模式英文名或 none>
decision: adopt | reject
pressure: <当前、具体、可定位的设计压力>
expected_benefit: <可验证的净收益；无收益时说明 none>
simpler_alternative: <更简单的方案及其是否足够>
application: <最小作用域、参与者、职责、数据流与验收方式>
costs_and_rejections: <引入成本、失败模式、拒绝的相邻模式>
```

## 快速索引

| 真实设计压力 | 首先考察 | 先排除的误用 |
| --- | --- | --- |
| 创建具体类型会污染业务流程 | 工厂方法、抽象工厂 | 只有一个稳定类型却建立工厂层级 |
| 同一复杂对象有多种构造过程或表示 | 建造者 | 仅为可选参数创建大量 Builder 方法 |
| 初始化昂贵且已有合格样本 | 原型 | 未定义深浅拷贝和资源所有权 |
| 进程内必须唯一且生命周期受控 | 单例 | 把普通共享依赖变成全局可变状态 |
| 两个既有接口不兼容 | 适配器 | 顺便加入缓存、权限等额外职责 |
| 两个维度确实独立变化 | 桥接 | 只有单一维度却建立双层继承/组合 |
| 叶子与容器需要统一递归操作 | 组合 | 强迫叶子实现无意义的子节点 API |
| 行为需要按实例、按运行时叠加 | 装饰 | 包装层改变核心语义或依赖顺序不明 |
| 子系统接口过多且调用顺序复杂 | 外观 | 隐藏仍需暴露的重要能力和错误信息 |
| 海量对象重复持有不可变大状态 | 享元 | 规模没有内存证据却拆分内外状态 |
| 访问真实对象前后需要透明控制 | 代理 | 代理接口与真实对象语义不一致 |
| 多个处理者按可变顺序尝试请求 | 责任链 | 路由固定且单一却创建动态链 |
| 请求需排队、记录、重试或撤销 | 命令 | 一次普通调用被无意义对象化 |
| 集合表示需隐藏且遍历方式可替换 | 迭代器 | 语言原生迭代协议已足够仍另造接口 |
| 多组件形成网状依赖 | 中介者 | 生成知道一切的“上帝对象” |
| 要在不泄露内部结构下恢复快照 | 备忘录 | 保存敏感、不可序列化或无限增长状态 |
| 一对多事件通知且订阅关系动态 | 观察者 | 用事件掩盖关键同步调用链 |
| 行为随有限状态变化且迁移受约束 | 状态 | 仅有少量稳定分支却拆成许多类 |
| 多个算法可互换且选择点明确 | 策略 | 算法从不替换却提前抽象 |
| 稳定流程骨架允许少量步骤变化 | 模板方法 | 用继承替代更简单的组合 |
| 对稳定对象结构持续增加新操作 | 访问者 | 元素类型经常变化导致双重维护 |

## 创建型模式

创建型模式关注对象如何被构造、选择和复用。它们的价值在于把创建决策从使用者移开，而不是把每次构造都包装成
工厂。

### 1. 工厂方法（Factory Method）

- **意图**：让上层流程依赖一种产品契约，把具体产品的创建留给可替换的创建点或子类型。
- **适用压力**：核心流程稳定，但实际创建类型由运行环境、插件、协议或子类决定；调用者不应散布具体构造器。
- **成立收益**：新增产品时减少对稳定流程的修改，集中构造校验，并让测试替换创建结果。
- **正确应用**：定义最小产品接口；创建者暴露一个返回该接口的工厂方法；业务流程只使用产品接口；具体创建者只负责
  选择和实例化，不吞并产品业务。
- **代价与拒绝**：会增加类型和间接层。若类型唯一、构造稳定，普通构造函数、参数化函数或依赖注入更清楚。
- **易混淆**：抽象工厂创建一整族相容对象；工厂方法通常解决一个产品创建点，并可作为抽象工厂的内部实现。

### 2. 抽象工厂（Abstract Factory）

- **意图**：通过一个族级接口创建彼此相容的一组产品，而不让调用者依赖各产品的具体类。
- **适用压力**：UI 主题、数据库方言、云提供商或协议栈等场景要求多个组件成套切换，混用不同族会破坏约束。
- **成立收益**：把“产品必须成套”的不变量集中到一个工厂，整体替换实现族，并阻止错误组合。
- **正确应用**：先定义各产品的独立契约，再定义包含每种创建操作的工厂契约；每个具体工厂只产生同一族产品；组装根
  选择一次工厂并注入使用者。
- **代价与拒绝**：增加一种新产品类别时，所有工厂都要变化。若只切换单个对象或不存在族内相容性，工厂方法或直接注入
  更合适。
- **易混淆**：建造者处理同一复杂对象的分步构造；抽象工厂强调多种相关对象的成套产出。

### 3. 建造者（Builder）

- **意图**：把复杂对象的分步组装从最终表示中分离，使相同构建过程能够产生不同配置或表示。
- **适用压力**：构造步骤多、顺序或校验重要，构造参数组合爆炸，或者同一输入需要生成不同输出形式。
- **成立收益**：消除难读的巨型构造器，复用可靠步骤，集中完成态校验，并避免半初始化对象泄漏。
- **正确应用**：Builder 持有构建中的临时状态；每步只表达一个有意义的配置；`build` 在原子边界校验不变量并返回完整
  产品；需要固定流程时才增加 Director。
- **代价与拒绝**：引入额外可变状态和 API。参数很少、对象不可变构造已清楚时，命名构造函数或参数对象通常足够。
- **易混淆**：抽象工厂直接返回一族产品；建造者允许在多个步骤后返回一个复杂结果。

### 4. 原型（Prototype）

- **意图**：从已有、已配置好的对象复制新实例，避免调用者了解其具体类型和繁琐初始化细节。
- **适用压力**：创建成本高、运行时才知道类型、初始配置组合很多，且复制一个合格样本比重新构造可靠。
- **成立收益**：减少重复初始化，支持运行时注册新原型，并把复制规则留在最了解内部状态的对象附近。
- **正确应用**：明确浅拷贝与深拷贝边界；为可变子对象、句柄、锁、缓存和外部资源规定所有权；复制后重建必须唯一的
  身份；用测试证明原型与副本不会意外共享可变状态。
- **代价与拒绝**：循环对象图和外部资源使复制复杂。普通值对象、廉价构造或可靠序列化工厂已足够时不采用。
- **易混淆**：备忘录保存并恢复同一对象的历史状态；原型的目标是创建另一个可独立使用的对象。

### 5. 单例（Singleton）

- **意图**：在一个明确作用域内保证某类型最多只有一个实例，并提供受控的获取方式。
- **适用压力**：底层资源在技术上必须唯一，例如进程级协调器或硬件句柄，且重复实例会破坏正确性。
- **成立收益**：唯一性和初始化时序成为可验证不变量，避免重复占用排他资源。
- **正确应用**：优先由应用组装根创建一个实例并通过依赖注入共享；若必须自管理，处理并发初始化、失败重试、关闭和
  测试替换；保持接口小且状态受控。
- **代价与拒绝**：全局访问隐藏依赖、制造跨测试污染和并发瓶颈。仅仅“大家都要用”不构成采用理由。
- **易混淆**：共享实例不必等于单例；容器中的 scoped dependency 往往能提供同样生命周期收益而没有全局状态。

## 结构型模式

结构型模式处理对象或类型之间的组合关系。正确使用时，外部看到稳定边界，内部仍能替换；错误使用时，则会形成只做
转发的层层包装。

### 6. 适配器（Adapter）

- **意图**：把一个既有对象的接口转换成调用方期待的接口，使原本不兼容的双方协作。
- **适用压力**：需要接入第三方、遗留或跨协议组件，双方接口均不宜或不能直接修改。
- **成立收益**：兼容逻辑集中，核心领域不受外部数据形状和命名污染，并形成可替换的测试边界。
- **正确应用**：目标接口表达调用方真正需要的语义；适配器只做参数、结果、错误和单位转换；明确同步/异步、幂等和
  生命周期差异；契约测试覆盖语义等价而非仅类型匹配。
- **代价与拒绝**：多一层映射和故障点。若能够安全统一原接口，应直接重构，不长期保留双重术语。
- **易混淆**：外观简化一个复杂子系统；适配器解决两个具体接口不兼容；代理保持相同接口并控制访问。

### 7. 桥接（Bridge）

- **意图**：把抽象能力与底层实现分成两个通过组合连接、可独立演进的维度。
- **适用压力**：例如“消息类型 × 发送渠道”或“控件 × 平台”两个维度都会扩展，单一继承层级会产生组合爆炸。
- **成立收益**：新增一个维度的成员不再复制另一维度的所有组合，平台细节与业务抽象可以独立测试和发布。
- **正确应用**：确认两个变化轴都真实存在；高层抽象持有实现接口；实现接口只暴露底层原语，高层组合这些原语形成业务
  行为；依赖方向由抽象指向实现契约。
- **代价与拒绝**：双层 API 增加理解成本。只有一个变化轴或组合数量很小稳定时，普通组合或策略更简单。
- **易混淆**：策略替换一个算法；桥接通常从系统设计之初分离两个长期独立演进的层次。

### 8. 组合（Composite）

- **意图**：把叶子与容器组织成树，并让调用者通过共同契约统一处理单个对象和对象集合。
- **适用压力**：文件树、UI 树、表达式、组织结构等天然递归结构，需要在任意子树上执行相同操作。
- **成立收益**：递归算法集中，调用者无需反复判断叶子与容器，新增节点类型可以保持遍历逻辑稳定。
- **正确应用**：共同接口只放叶子和容器都真正支持的操作；子节点管理优先留在容器；明确父子所有权、环检测、遍历顺序
  和失败聚合语义。
- **代价与拒绝**：过宽接口会迫使叶子提供无意义方法，统一处理也可能隐藏类型约束。结构不是树或操作差异很大时拒绝。
- **易混淆**：装饰通常是单子节点包装并增加行为；组合通常持有多个同类子节点并表达部分—整体关系。

### 9. 装饰（Decorator）

- **意图**：通过遵守同一契约的包装对象，在单个实例上动态叠加职责。
- **适用压力**：日志、压缩、重试、指标等正交行为需要灵活组合，继承会产生大量排列子类。
- **成立收益**：按实例选择行为、复用小职责，并避免组合数量导致的继承爆炸。
- **正确应用**：装饰器实现与被包装对象相同的契约并委托核心行为；每层只增加一个清晰职责；规定顺序、错误传播、身份
  和关闭语义；测试关键排列。
- **代价与拒绝**：层级过深时调试和对象身份困难，顺序可能改变结果。行为固定或只有一种组合时直接实现更清楚。
- **易混淆**：代理重点是访问控制或延迟；装饰重点是叠加可见职责；适配器通常改变接口。

### 10. 外观（Facade）

- **意图**：为复杂子系统提供一个面向常见用例的高层入口，同时允许必要时绕过它使用底层能力。
- **适用压力**：客户端必须知道过多类型、顺序和配置才能完成常见任务，或外部依赖正在污染领域代码。
- **成立收益**：降低常见调用的认知负担和耦合，集中正确调用顺序，并形成子系统演进的防腐边界。
- **正确应用**：按真实用例设计少量高层操作；保留重要错误和事务语义；外观负责协调而非吸收全部业务；复杂高级能力可
  继续通过底层接口显式访问。
- **代价与拒绝**：外观容易膨胀为上帝对象或掩盖关键能力。子系统本来就简单时无需再包一层。
- **易混淆**：适配器为了接口兼容；外观为了易用性和边界稳定，未必与底层保持同一接口。

### 11. 享元（Flyweight）

- **意图**：让大量细粒度对象共享不可变的内在状态，把每个实例独有的外在状态留给调用者传入。
- **适用压力**：性能测量表明对象数量和重复大状态造成显著内存压力，且重复部分可以可靠地不可变化。
- **成立收益**：在相同语义下显著降低内存和初始化成本；共享对象可缓存并复用。
- **正确应用**：先测量再设计；严格区分内在/外在状态；共享部分不可变且线程安全；工厂按稳定键缓存；调用时显式提供
  外在状态；监控缓存上限与淘汰。
- **代价与拒绝**：状态拆分增加调用复杂度和 CPU 成本，错误共享会串数据。没有规模证据、对象已很小或状态高度可变时
  拒绝。
- **易混淆**：对象池复用可变对象的生命周期；享元让多个逻辑对象同时共享不可变状态。

### 12. 代理（Proxy）

- **意图**：提供与真实对象相同或兼容的替身，在请求到达真实对象前后控制访问。
- **适用压力**：需要延迟加载、远程访问、权限校验、缓存、限流或生命周期控制，而调用者应继续面向稳定契约。
- **成立收益**：横切访问策略从业务对象分离，昂贵资源按需创建，远端或受保护对象可透明替换。
- **正确应用**：代理与真实对象保持契约和错误语义；明确哪些行为可缓存或重试；权限必须默认拒绝；远程代理不能假装
  网络与本地调用拥有相同延迟和失败特性；资源释放可追踪。
- **代价与拒绝**：隐藏的 I/O、缓存或重试会制造意外性能和一致性问题。调用语义明显不同或透明性会误导时，应使用显式
  网关接口。
- **易混淆**：装饰增加业务可见行为；代理控制访问；外观提供不同的简化入口。

## 行为型模式

行为型模式关注职责如何分配、请求如何流动，以及算法或状态如何变化。它们应让控制流更可见，而不是把简单调用链藏进
对象网络。

### 13. 责任链（Chain of Responsibility）

- **意图**：让请求沿有序处理者链传播，每个处理者决定处理、补充处理、终止或交给后继。
- **适用压力**：处理者集合或顺序需运行时配置，发送者不应知道最终处理者，例如中间件、校验或审批链。
- **成立收益**：发送者与处理者解耦，链可组合、插拔和单独测试，公共前后处理能够复用。
- **正确应用**：定义处理结果（已处理、继续、拒绝、失败）；顺序显式且可观测；保证未处理请求有最终语义；避免重复执行
  非幂等操作；限制链长度和递归风险。
- **代价与拒绝**：请求可能静默落空，控制流和性能更难追踪。处理者固定、只有一个目标时普通调用序列更可靠。
- **易混淆**：装饰通常每层都会执行；责任链的某个处理者可以终止传播或跳过处理。

### 14. 命令（Command）

- **意图**：把一次请求及其必要参数封装成独立值，使请求能被传递、排队、记录、重试、组合或撤销。
- **适用压力**：发起者与执行者需要解耦，操作具有调度生命周期，或者需要审计、宏命令和撤销能力。
- **成立收益**：请求成为可管理数据，队列和历史记录统一，调用方无需了解执行细节。
- **正确应用**：命令包含执行所需的最小不可变输入；执行者依赖明确；定义幂等键、重试和失败语义；撤销必须保存足够状态
  且明确不可逆边界；敏感参数不得进入不安全日志。
- **代价与拒绝**：每种简单操作都建类会膨胀。若无需延迟、历史、重试或解耦，直接函数调用或闭包更合适。
- **易混淆**：策略表示可互换的算法；命令表示一次可调度的动作实例。

### 15. 迭代器（Iterator）

- **意图**：在不暴露集合内部表示的前提下，提供一致、可暂停的元素访问顺序。
- **适用压力**：集合有多种遍历方式、内部结构复杂，或调用方不应依赖数组、树、图等具体存储。
- **成立收益**：遍历算法与集合解耦，同一集合可以并行拥有多个遍历状态，内部表示可替换。
- **正确应用**：优先实现语言原生迭代协议；规定顺序、空集合、并发修改、懒加载、资源关闭和异常语义；无限序列必须可
  取消；图遍历要防环。
- **代价与拒绝**：自定义迭代抽象可能重复语言能力并增加状态对象。简单稳定集合直接使用原生遍历即可。
- **易混淆**：访问者在遍历中按元素类型分派操作；迭代器只负责如何依次取得元素。

### 16. 中介者（Mediator）

- **意图**：把多个组件之间的协调规则集中到一个协作对象，减少组件彼此直接依赖。
- **适用压力**：组件形成难以维护的网状调用，单个组件复用时必须携带大量邻居，交互规则散落各处。
- **成立收益**：组件只依赖中介契约，交互流程集中测试，组件可独立替换。
- **正确应用**：中介者负责协作编排而非组件内部业务；事件和命令方向清晰；避免双向隐式回调；按业务子域拆分过大的
  中介；记录关键流程和失败补偿。
- **代价与拒绝**：中心对象可能变成上帝对象和性能瓶颈。只有少量清晰依赖时，直接协作更直观。
- **易混淆**：观察者广播事件且通常不掌握整体流程；中介者明确协调一组参与者的交互。

### 17. 备忘录（Memento）

- **意图**：在不向外暴露对象内部结构的情况下保存一个可恢复快照，并由外部保管其历史。
- **适用压力**：编辑器撤销、事务补偿或试算需要回到旧状态，同时必须维持对象封装。
- **成立收益**：恢复机制不依赖内部字段，历史管理与领域对象分离，快照可以形成清晰的事务边界。
- **正确应用**：对象自己创建和恢复不透明快照；保管者只管理顺序与保留策略；定义完整/增量快照、版本兼容、容量上限、
  加密与敏感字段排除；恢复后重新验证不变量。
- **代价与拒绝**：大对象或高频快照会消耗内存与 I/O，外部资源往往无法直接恢复。可逆命令或事件重放更简单时优先使用。
- **易混淆**：原型复制对象用于新实例；备忘录保存历史以恢复原对象。

### 18. 观察者（Observer）

- **意图**：建立动态的一对多订阅关系，在主题发生事件时通知所有当前订阅者。
- **适用压力**：多个独立消费者关心同一事件，消费者集合会变化，发布者不应依赖具体消费者。
- **成立收益**：发布者与消费者解耦，新消费者无需修改发布者，事件反应可独立部署或测试。
- **正确应用**：事件表达已经发生的事实；定义同步/异步、顺序、重复、丢失、背压和失败隔离；订阅必须可取消以防泄漏；
  事件负载小而稳定；关键业务链路保留可追踪关联。
- **代价与拒绝**：隐式控制流、通知风暴和最终一致性会增加调试成本。只有一个固定消费者或必须立即得到结果时直接调用。
- **易混淆**：中介者掌握交互编排；观察者的发布者通常不知道订阅者如何响应。

### 19. 状态（State）

- **意图**：把随有限状态变化的行为与迁移规则封装起来，使上下文委托给当前状态处理。
- **适用压力**：条件分支反复检查同一状态，行为与合法迁移复杂，增加新状态会修改许多方法。
- **成立收益**：每个状态的行为和迁移集中，非法迁移可明确拒绝，状态相关测试更局部。
- **正确应用**：先画出有限状态与迁移表；上下文拥有当前状态；状态对象只处理该状态的行为并通过受控入口迁移；确保
  持久化、并发和重放语义；简单无数据状态可共享。
- **代价与拒绝**：状态很少且稳定时会制造类碎片；迁移散到状态对象后也可能难以总览，应保留机器可读状态图或表。
- **易混淆**：策略通常由调用方选择并可自由替换；状态由内部生命周期驱动，迁移受到规则限制。

### 20. 策略（Strategy）

- **意图**：把一族可互换算法放到共同契约后，由上下文或组装根选择具体实现。
- **适用压力**：排序、计价、路由、压缩等算法有多个真实变体，条件分支不断增长，且每种算法需要独立测试。
- **成立收益**：算法可以替换和组合，调用流程保持稳定，变体测试与性能比较更直接。
- **正确应用**：契约表达算法共同输入输出与错误；策略尽量无状态或明确生命周期；选择逻辑留在边界；不泄漏具体策略
  细节；用同一契约测试验证所有实现。
- **代价与拒绝**：调用者可能必须理解差异，过多微型策略增加文件和对象数量。只有一个稳定算法或简单参数足够时拒绝。
- **易混淆**：命令封装一次动作；状态随生命周期切换；桥接分离两个结构维度。

### 21. 模板方法（Template Method）

- **意图**：在基类中固定算法骨架和不变量，只允许子类覆盖少量明确步骤。
- **适用压力**：多个流程共享严格顺序和大部分步骤，但在少数位置存在稳定变体，而且继承关系本身合理。
- **成立收益**：公共流程只维护一次，关键顺序不能被子类破坏，受控扩展点减少重复。
- **正确应用**：模板入口通常不可被任意覆盖；抽象步骤最少且语义清楚；钩子提供安全默认值；基类负责全局不变量和错误
  处理；遵守替换原则并测试每个子类。
- **代价与拒绝**：继承形成强耦合，钩子过多会出现脆弱基类。现代代码中，函数组合或注入策略往往更简单灵活。
- **易混淆**：策略通过组合替换整个算法或步骤；模板方法通过继承固定骨架。

### 22. 访问者（Visitor）

- **意图**：把作用于稳定元素结构的新操作移到独立访问者中，并通过双重分派选择类型相关行为。
- **适用压力**：元素类型集合稳定，但需要频繁增加跨多种元素的操作；把每个操作塞回元素会污染领域模型。
- **成立收益**：一种操作的所有类型分支集中，新操作无需修改每个元素的业务实现，并可在遍历中积累状态。
- **正确应用**：每个元素提供 `accept`，访问者为每种具体元素提供明确操作；元素层级必须相对稳定；定义遍历所有权、返回值、
  错误和跨元素状态；不要通过访问者破坏元素封装。
- **代价与拒绝**：新增元素类型会迫使所有访问者修改，且双重分派增加理解成本。元素类型常变或操作很少时直接方法、
  模式匹配或函数表更合适。
- **易混淆**：迭代器负责访问顺序；访问者负责对不同元素类型执行什么操作，两者可以组合。

## 模式组合与冲突检查

模式可以组合，但每多一个模式都必须独立通过收益门槛：

- 抽象工厂可用工厂方法实现具体创建操作；不要因此向每个构造器都加两层抽象。
- 桥接可在实现维度使用策略；只有两个真实变化轴都存在时才保留两种抽象。
- 组合可配合迭代器遍历、配合访问者执行类型相关操作；先确认树结构和新操作频率都真实存在。
- 装饰、代理和适配器都可能包装对象，但职责必须单一：叠加行为、控制访问、转换接口不可含混。
- 命令可配合备忘录实现撤销；先判断逆操作或事件记录是否已经足够。
- 中介者可能发布观察者事件，但关键同步流程不得因此变成无法追踪的事件网。
- 状态对象内部可使用策略算法；若状态只是在选择算法，应直接使用策略而非双重结构。

最终检查：删掉模式名称后，设计仍应能用清楚的职责、数据流、不变量和验收标准解释。如果只能靠模式名称说明设计，说明
设计尚未具体；如果移除模式后代码更短、更清晰且仍满足所有当前要求，应拒绝或移除该模式。
