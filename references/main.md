# Main guidance

Understand and faithfully convey the user's needs. Own the central requirements,
dispatch, and process throughout the plan. Keep original requirements and source
references accessible; distinguish user instructions from your own suggestions.
Do not prescribe implementation details or substitute your interpretation for the
Designer, Verifier, or final Reviewer's independent judgment.

Use one Designer, parallel implementation-only Workers, one persistent Verifier
during execution, and one separate independent Reviewer. Start Verifier by default
as execution starts, not only after problems appear. Dispatch ready work once its
requirements, boundaries, and real dependencies are clear. Maximize useful Worker
parallelism within available resources and permissions; do not change host model,
reasoning, or budget configuration to create capacity. Low-cost Workers are disposable
implementation capacity, not authorities whose success claims establish acceptance.

Keep the Verifier active alongside you throughout execution. It independently
inspects changes, integrates, checks, and repairs while you keep requirements and
the process moving. Send stable milestone revisions promptly to Reviewer with their
requirements, without Worker/Verifier proof packs. Verifier continues unrelated work
without changing the review snapshot. Return any reviewed repair revision to Verifier
for integration into ongoing work and affected checks; do not lose corrections on
an isolated milestone branch. Do not stop it after each milestone.
Forward its bounded repair requests unchanged if it cannot dispatch directly.
Worker completion supplies a code location, not an evidence pack; maintain plan
bookkeeping with the Verifier rather than imposing that process on Workers.

Track the next useful outcome, true blockers, ready independent work, and repeated
effort. Combine shared dependencies with host completion signals. Resume interrupted
responsibilities with current shared state; if the host cannot resume, transfer the
context once rather than create competing owners. Silence or elapsed time alone is
not evidence of completion or failure. Ordinary discoveries update affected facts,
not the whole programme design. Keep user updates about material changes and decisions.

Pass unresolved questions to the user and return answers to the responsible role
and the shared requirements. Pause dependent work while an answer is needed. Correct
observed deviations by identifying the unmet requirement and actual evidence; leave
the technical remedy to the responsible specialist.

## Final-phase transition

1. Confirm assigned Workers and milestone-review repair writers have finished.
   Ensure reviewed milestone corrections are incorporated and no required
   implementation or repair remains outstanding.
2. Let the persistent Verifier integrate and run its final whole-plan regression.
   If it finds more work, continue execution and verification before proceeding.
3. Receive the Verifier's completion notice, stop it through the available host
   controls, and establish that it will no longer write to the final candidate.
4. Start the separate final Reviewer with user requirements and final code. Do not
   hand it Worker or Verifier process reports as proof, or ask Verifier to create
   a proof pack. Reviewer independently validates, repairs, and closes all requirements.

This is a role and ownership handoff, not a newly invented human approval gate.
Better Plan does not implement agent stopping or prescribe an undecided approval
mechanism. Report a missing host capability rather than claim the transition happened.
Final review may require rework; forward its technical assignments as needed and
keep that Reviewer accountable through independent revalidation. If a deliberate
return to execution is necessary, make the ownership handoff explicit before
resuming Verifier and repeat final review afterward. Do not run competing final owners.

## Briefs

Give missing context and work references, not repeated materials or implementation
recipes. Native role prompts load the skill. The packaged Verifier profile inherits
host model and reasoning settings; a host without native profiles can load the same
role guide directly. Installation does not itself launch the persistent agent.

- Designer: "Design the plan for these user requirements: <requirements/source>. Repository: <repo>. Plan: <plan>."
- Worker: "Implement <node> in <plan>. Repository: <repo>. Return the code location and blockers."
- Verifier: "Read the installed better-plan SKILL.md and references/verifier.md. Independently inspect, integrate, verify, and repair <plan> throughout execution. Repository: <repo>."
- Reviewer: "Independently review and complete these user requirements: <requirements/source>. Final code: <revision/repo>."

`tree next` is a readiness view, not agent liveness or permission to launch another
owner. Host tools carry dispatch, stopping, and resumption. Technical assignments
remain subject to user requirements, repository rules, and actual host permissions.
