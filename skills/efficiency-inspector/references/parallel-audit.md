# 并发审计建议

效率督查经常需要搜索多个根对话。根对话之间通常相互独立，因此并发搜索和取证可以明显缩短
整体时间；并发是一项优先策略，不是完成审计的前置门禁。

## 选择执行方式

先估算根对话数量 `R`、可形成的互斥 shard 数 `K`、可用子槽 `C` 和每个 shard 的工作量。

- 当 `K >= 2` 且 `C >= 2` 时，优先首波派发 `min(K, C)` 个审计员。
- 根数量多于槽位时，在一个 shard 中放入多个互斥根，或在槽位释放后补派下一 shard。
- 容量只有一个、样本只有一个或后续取证依赖前序结果时，采用串行方式。
- 宿主并发不稳定时，使用较小波次；统计口径、目录结构和根所有权保持一致。

推荐的两槽三 shard 顺序是：

```text
spawn(A), spawn(B), wait(in-flight set), terminal(A or B), spawn(C), wait(in-flight set)
```

串行环境可以使用：

```text
audit(A), aggregate-local(A), audit(B), aggregate-local(B)
```

最终报告记录采用了并发、分波次还是串行，便于后续比较协调成本。

## 并发发现

候选根本身需要搜索时，可以按互不重叠的时间段、索引范围或存储分区分配 finder。每个 finder
把安全候选标签写入自己的 discovery 文件，协调者去重后冻结根清单和共同 cutoff。

搜索空间较小或只能由一个读取入口顺序访问时，协调者可以直接完成发现，再并发后续取证。

## 分片和文件所有权

以根对话作为统计所有权单元，把相关后代与根放入同一 shard。不同审计员获得不同根集合和独立
输出路径。按照 [数据目录与并发写入](data-layout.md) 为每个审计员分配：

```text
observations/token/shard-NNN.jsonl
observations/timeout/shard-NNN.jsonl
findings/shard-NNN.md
```

独立路径让各审计员可以同时工作而不会争用同一文件。若两个能力由不同审计员完成，可分别分配
token 与 timeout 路径；协调者在 manifest 中记录清楚所有权。

## 审计员任务说明

可以向每个审计员提供如下任务：

```text
使用 $efficiency-inspector 审计分配的根对话，并采用批次共同 UTC cutoff。
只读原始对话，沿父子关系和时间线发现 Token、监督行为与执行时间。
结合上下文判断监督有效性，把标准化观察写入分配的 JSONL，把判断理由、异常值和建议写入
finding 文件。只处理分配范围，完成后返回文件路径和简短摘要。
```

审计员在自己的范围内发挥判断力：识别新行为标签，解释有效或低效监督，复核高消耗样本，并在
需要时编写或调整任务内工具。

## 等待与补位

同时有多个在途审计员时，优先使用集合式或事件驱动等待，一次覆盖所有在途任务。收到某个终态
后先处理其增量结果，再决定是否补派。宿主只提供单目标等待时，按宿主接口逐个等待，并尽量减少
没有新状态的重复查询。

spawn 表示已经派发，final callback 表示交付完成。wait timeout、沉默或运行时间较长通常只表示
任务仍在进行；结合宿主状态和上下文决定继续等待、追问、重试或改为串行处理。

重试使用新的 attempt 文件，协调者在 manifest 中选定最终采用的结果。聚合时只输入选中的
attempt。

## 聚合

协调者可以在各 shard 完成时做增量检查，并在当前统计批次的文件集合确定后生成最终汇总。加总
原始 Token 分量后重算整体比率；不同大小 shard 的百分比直接平均会产生偏差。

建议报告：

- 根数量、shard 数、并发宽度与实际执行模式；
- 每个 shard 的 Token、时长、监督有效性和异常值；
- 聚合 Token 与时间结果；
- 子智能体协调本身消耗的 Token 和时间；
- 不同执行方式对监督成本的可能影响。

评价子智能体是否提高效能时，最好设计同任务、同源码状态、同验收边界和同模型的主线程单独
执行对照。没有完整对照时，也可以给出基于现有行为与分布的分析，但要说明它属于观察性判断。
