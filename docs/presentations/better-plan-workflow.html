01 / The shared blackboard

共享计划。
自主协作。
完整收敛。

主智能体把用户的需求传清楚。
每个角色用自己的判断，把工作做好。

所有角色直接阅读同一份事实

用户需求与原始材料

当前计划、依赖与待决问题

仓库文档、代码与项目规则

执行结果、验证证据与历史来源

辅助工具维护共享信息；角色指引传递职责。任务派发只补必要的上下文。

02 / The workflow

一个设计者，并行执行者，一个复核者。

并行发生在执行阶段。收敛阶段由同一个 Reviewer 连续负责。

1 Designer

理解长期需求
自主设计与分解

→
N Workers
W₁W₂W₃…Wₙ

真实依赖下尽可能并行

→
1 Reviewer

独立审视 · 直接修复
最终集成 · 验证结果

进入收尾前，其他写入者已结束。Reviewer 发现遗漏后继续修复，不再叠加 Reviewer，也不引入独立集成智能体。

03 / Main

对需求负责。
让流程持续运转。

理解需求，传达需求。
该恢复时恢复，
该启动下一步时启动。

01

理解用户的真实目标，完整传达来源与要求。

02

跟踪完成和中断，恢复原负责者，衔接下一步。

03

把子智能体的疑问转达用户，将答案同步回共享计划。

04

发现偏差立即指出事实，让负责角色判断如何修正。

04 / Design & execution

DESIGNER

长期目标需要什么，
就设计什么。

架构、代码、文档、工作流、脚本、工具，都是实现用户目标的手段。Designer 自主选择方案与分工。

遵守用户要求与仓库规则。设计出真实依赖和可并行的工作。
WORKER

给出工作定位，
让它自主完成。

Execute <node> in <plan>.
Repository: <repo>.

Worker 自己读取技能、计划和仓库，自主实施、解决问题、验证并记录结果。

节点说明它负责的贡献，不是文件访问白名单，也不是主智能体规定的实现步骤。

05 / Independent convergence

Reviewer 审视的，
也包括计划本身。

带着独立眼光检查实际结果。发现问题就直接修复，直到满足用户需求与设计初衷。

审视 → 修复 → 验证 → 集成
同一个负责者，完成整个收口。

  • 用户需求实现的结果是否真正解决用户的问题？
  • 业界最佳实践实现质量、结构与验证是否可靠？
  • 仓库规则是否符合项目的真实要求？
  • 设计与执行计划是否有效？设计有无遗漏？执行是否偏离？

06 / Continuity & clarification

不确定就反馈。中断就接续。

QUESTION

出现未决信息

子智能体主动反馈 → main 转达用户 → 答案回到负责者与共享计划。依赖答案的工作可以暂停。

INTERRUPTION

执行意外中断

通过宿主恢复原智能体。确实无法恢复时，交接已有上下文和责任，避免两个负责者同时工作。

CORRECTION

发现结果有遗漏

main 说明未满足的需求与证据 → 原 Reviewer 自主判断并继续修复。一次等待返回不代表工作已结束。

差异化视角的价值，在于主动发现未知信息。模糊计划不应靠猜测继续推进。

07 / The actual prompts

短派单，直接加载角色指引。

角色职责

派发示例 · 只补必要定位
右侧为本次交付的源文件原文快照。角色指引包含执行所需机制；可切换查看所有角色共用的 SKILL.md。模型与权限留在宿主配置中。


08 / Tools that earn their place
工具承担机械工作，智能体保留判断。
需要共享计划工具宿主能力
直接了解当前工作node show/start、tree export读取仓库与项目材料
衔接下一项工作tree next 提供依赖与就绪信息派发、完成通知、消息
提出疑问与恢复工作共享待决问题、当前结果、历史来源转达用户、恢复同一会话
记录真实验证与收敛checks、task/tree finish执行验证与 Git 操作
就绪状态不证明智能体已退出；完成记录不代替独立复核。主智能体结合共享事实与宿主执行状态衔接流程。
