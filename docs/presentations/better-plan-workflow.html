03 / Main

对需求负责。
让流程持续运转。

理解并传达需求。
识别真正的阻塞，
启动就绪工作并减少重复。

01

理解用户的真实目标，完整传达来源与要求。

02

跟踪真实依赖与就绪工作，恢复原负责者，衔接下一步。

03

把子智能体的疑问转达用户，将答案同步回共享计划。

04

指出偏差和重复工作，交由负责角色判断修复方案。

04 / Design & execution

DESIGNER

需求映射到架构，
就绪工作及时交接。

Designer 明确完整可交付的里程碑、真实依赖与共享边界，让工作尽可能并行；不预先穷尽实现细节或预知运行时错误。

可独立交付的旧缺陷修复、必要重构与新功能分别划界；功能实现中的错误仍在原工作内修复。职责变轻不改变宿主模型配置。
WORKER

给出工作定位，
让它自主完成。

Execute <node> in <plan>.
Repository: <repo>.

Worker 自主选择实现细节、处理边界情况与运行时问题，验证并记录结果；发现新情况只调整受影响的计划。

节点说明它负责的贡献，不是文件访问白名单，也不是主智能体规定的实现步骤。

05 / Independent convergence

Reviewer 审视的，
也包括计划本身。

带着独立眼光检查实际结果。直接修复问题，或委派边界清晰的独立修复，并审阅其源码。

及时完成里程碑收口
同一个负责者，兜底全部需求。

  • 用户需求逐项核对全部已记录需求，包括计划遗漏；覆盖关联不等于满足需求。
  • 业界最佳实践实现质量、结构与验证是否可靠？
  • 仓库规则是否符合项目的真实要求？
  • 设计与执行计划是否有效？设计有无遗漏？执行是否偏离？

06 / Continuity & clarification

不确定就反馈。中断就接续。

QUESTION

出现未决信息

子智能体主动反馈 → main 转达用户 → 答案回到负责者与共享计划。依赖答案的工作可以暂停。

INTERRUPTION

执行意外中断

通过宿主恢复原智能体。确实无法恢复时，交接已有上下文和责任，避免两个负责者同时工作。

CORRECTION

发现结果有遗漏

main 说明未满足的需求与证据 → 原 Reviewer 自主判断并继续修复。只冻结正在验证的候选；独立修复可以并行推进。

差异化视角的价值，在于主动发现未知信息。模糊计划不应靠猜测继续推进。
